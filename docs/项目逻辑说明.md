# 项目逻辑说明

本文按当前代码说明抢票脚本的运行链路、页面操作、验证码处理和安全边界。文档只描述已经实现的行为；页面结构变化时，以 `calibrate` 生成的现场信息和源代码为准。

## 1. 项目边界

项目运行在 Windows + Python 3.12 + Playwright Chromium 环境中，用于访问北航羽毛球场预约页面，完成登录后的场地检索、场地选择、同伴选择、协议确认和订单提交。

提交订单可产生真实预约结果，因此正式流程和真实流程测试都**需要明确授权**。程序进入支付页后会点击付款入口、生成二维码并发送到手机，但不会点击最终支付确认按钮。

验证码支持人工模式和本地自动 clickword 模式。自动模式只处理页面提交后捕获到的 `captcha/get` JSON，不向第三方验证码服务上传图片。

## 2. 总体运行链路

```text
计划/配置
  -> 登录并打开场馆页面
  -> 选择目标日期
  -> 读取场地矩阵或候选选择器
  -> 选择场地
  -> 选择同伴
  -> 勾选预约须知
  -> 等待可点击的提交按钮
  -> 提交并监测页面/网络响应
  -> 处理验证码、占用、同伴缺失或支付页
```

主要入口是 `python -m buaa_booking`，核心浏览器流程在 `src/buaa_booking/automation.py`。

## 3. 代码模块职责

| 模块 | 职责 |
|---|---|
| `models.py` | 计划、场地、运行状态和事件等数据模型，以及时间和字段校验 |
| `config.py` | 读取 JSON 配置，合并默认值并校验运行参数 |
| `secrets.py` | 通过 Windows Credential Manager 保存和读取账号、密码、Bark key 等敏感信息 |
| `store.py` | SQLite 运行状态、事件和计划持久化 |
| `dashboard.py` | 提供手机设置页、计划确认接口和本地运行状态页 |
| `cli.py` | `init`、`setup-secrets`、`serve`、`prompt`、`run`、`calibrate` 等命令入口 |
| `automation.py` | Playwright 登录、日期、场地、同伴、协议、提交和提交后状态处理 |
| `captcha.py` | clickword 图片解析、OCR、目标字符匹配和坐标点击 |
| `calibration.py` | 页面元素盘点、截图和脱敏后的结构检查结果 |
| `notifier.py` | Console/Bark 通知和远程操作入口通知 |
| `tasks.py` | 根据手机反馈和计划确认状态启用或停用提醒任务 |

## 4. 计划和运行状态

计划由 `DailyPlan` 表示，包含运行日期、目标日期、开始/结束时间、是否启用和是否已确认等信息。手机设置页保存计划后，状态从草稿变为已确认；定时任务或 `run` 命令再读取该计划。

运行过程会写入 SQLite 事件。常见状态包括：

- `draft`：尚未确认计划；
- `confirmed`：计划已确认，等待运行；
- `running`：正在登录或查找场地；
- `captcha`：等待人工或自动验证码处理；
- `payment`：已进入支付页；
- `skipped`：当天计划未启用；
- `failed`：页面、网络、登录或流程校准失败。

## 5. 浏览器启动和登录

`automation.py` 使用 Playwright 持久化浏览器上下文，复用本地浏览器状态目录。启动后打开首页，未登录时尝试已有登录流程，必要时等待用户在可见浏览器中完成登录。首页显示“个人中心”只能作为初步判断；程序还会在等待开抢前检查场馆预约表格是否加载成功。

未登录时进入站点的独立登录页，等待异步加载的认证入口和账号密码表单。统一身份认证页面也有“个人中心”链接，因此只有返回预约站点后才接受登录标记。过期提示确认后若网站已转到登录页，则直接继续登录，无需再查找退出按钮。

等待日期控件和预约表格时，程序同时检查可见的登录过期提示。发现 Token 失效后，通过网站自身的退出确认和登录入口恢复会话，再重新加载各场馆页面。每次运行最多恢复一次；恢复后仍然过期则停止并报告登录错误。开抢后选择目标日期时也执行这项检查，避免把登录过期误报成日期控件未渲染。

场馆检查单独记录为“场馆校验”。如果网页提示“返回数据格式不正确”，程序立即识别，并只对出错场馆最多重新加载两次；重载后重新校验目标日期。持续失败时报告场馆编号和网页错误，不再只显示通用的 30 秒等待超时。这类数据错误本身不会触发退出登录。

流程默认打开配置中的场馆页面。两个场馆页面会分别处理，但候选场地会按配置的场馆优先级合并排序。

## 6. 日期选择和响应确认

日期选择不是只点击一次就结束。程序会：

1. 根据目标日期生成多个可能的日期文本；
2. 尝试配置中的日期选择器和页面可见日期按钮；
3. 点击日期后等待页面更新；
4. 监听预约查询响应，并确认请求中包含目标日期；
5. 只有日期和查询响应都符合预期时，才进入场地读取阶段。

这样可以避免页面仍停留在默认日期时误抢场地。

## 7. 场地候选读取

当前运行路径直接读取目标网页的 `.spaceTable > table`。脚本支持整点起止的一小时或连续两小时；例如 `16:00–18:00` 会拆成 `16:00–17:00` 和 `17:00–18:00`，分别查找对应表头，不再查找不存在的两小时合并列。

网页每页显示五个时间列，两个时段可以跨页。程序按表头翻页，并按单元格的 `colspan` 计算实际列位置，避免活动占用形成的合并单元格使后面的时间列错位。网站每页最后一个时段的 `colspan=2` 是排版补偿，仍按一个时段识别；真正跨多个时段的合并价格格不会被直接放行。候选须有唯一、可见的 `.reserveBlock.free`，显示价格、免费或可预约标记，且不存在禁用、占用或已预约状态。点击的是格内场地块，并核对实际已选时段。

两个时段在同一场馆内组合，一组候选覆盖完整时间范围。排序先比较是否同一块场地，再使用配置的场馆优先级：两个场馆的同场地连续组合优先于换场组合。没有同场地连续空位时，允许在同一场馆内第一小时和第二小时使用不同场地；不跨场馆拼成一笔预约。

多时段候选保存各自的场地号和小时段。点击前重新定位对应时段和场地行，不复用翻页前的列定位器。原有矩阵及几何定位辅助函数仍在代码中，但当前候选读取流程不调用这些旧分支。

每轮记录场馆、日期、时段、读取数量、可用数量、过滤原因和耗时；候选为空或状态不明时，将脱敏后的结构与状态追加到当天的 `candidate-snapshots.jsonl`，不保存原始单元格文本或整页 HTML。无法识别场地行、表头或价格格结构时报告解析错误，不等同于“没有场地”。

## 8. 页面点击逻辑

### 8.1 选择场地

进入候选循环后，程序先清除上一组残留的已选项，再依次选择这组候选的全部时段。每次点击后核对 `.selected_box` 内的场地号和时间，不能仅凭存在一个“已选”标记继续。尚未选场时该容器被网页隐藏，视为正常空选状态。

如果第二个格子已被占用或未成功选中，程序通过已选列表的删除按钮清掉第一个格子，再尝试下一组候选。全部时段选中后，只选择一次同伴、勾选一次须知，并在提交前再次核对完整组合，只提交一次。任一时段缺失时不提交一小时的部分订单；无法确认或清除已选项时停止。

旧候选全部失效后，按 `availability_refresh_interval_seconds` 间隔重新进入场馆、选择日期并重新扫描；最多额外重扫 `availability_refresh_count - 1` 次。首次读取和候选选择共用 `availability_timeout_seconds` 总时限，旧配置缺省为 15 秒。超时或重扫次数耗尽后停止，不提交部分订单；已成功选中后不把这个时限用于验证码或人工支付。点击后若已明确变为不可预约状态，则提前结束选中等待；页面正常延迟更新仍保留有限等待。

### 8.2 选择同伴

同伴选择由 `_select_first_companion` 和 `_click_first_companion_candidate` 完成：

1. 优先点击配置中的 `companion_open`，打开同伴区域；
2. 在“同伴”标题和“手机号”字段之间限定搜索范围；
3. 依次检查配置中的 `companion_options` 和内置候选选择器；
4. 排除“新增、添加、取消、提交、同伴、手机号码、预约须知”等控制文本，以及 `addBtn`/`add-btn` 元素；
5. 对可见、短文本、符合姓名/编号格式的候选执行强制点击；
6. 点击后检查 `.buddy-row` 的 class 是否出现 `active` 或 `is-active`；
7. 如果仍未确认，再尝试配置中的显式姓名和通用 `div`、`span`、`label`、`li`、`p` 元素。

只有确认同伴已选中后才进入协议和提交阶段。找不到可选同伴时抛出校准错误并停止，避免提交不完整订单。

### 8.3 勾选预约须知

程序通过 `agreement_checkbox` 找到预约须知复选框。如果尚未勾选就执行 `check()`，失败时退回普通点击；点击后再次读取选中状态。复选框不存在或仍未选中时停止流程。

### 8.4 等待提交按钮

程序不会只根据按钮文字点击提交。它会检查：

- 元素可见；
- 没有 `disabled` 或 `aria-disabled=true`；
- class/style 没有禁用状态、透明状态或禁止点击样式；
- 页面样式或 class 表现为可用的蓝色/主要按钮。

提交前会保存截图，并在点击前注册提交后的网络响应监视器。

## 9. 提交后的状态判断

点击提交后，程序同时观察页面文本、URL、嵌套 frame 和已捕获的网络响应，按结果处理：

- 出现验证码：转入人工或自动验证码流程；
- 出现同伴缺失：停止并要求校准；
- 订单冲突：检测与恢复方法仅作为备用保留，正常流程不调用，也不会自动刷新重提；
- 检测到支付页：进入支付状态并停止自动操作；
- 无法确认结果：保存截图和事件，停止，不继续盲目提交其他场地。

为避免重复下单，未知状态不会自动循环重试。

## 10. clickword 验证码

### 10.1 响应数据来源

提交后监听 `captcha/get`。当响应类型为 `application/json` 时，程序解析顶层对象以及 `data`/`repData` 对象，读取：

- `originalImageBase64`：验证码原图；
- `wordList`：需要点击的字符列表；
- `token`、`secretKey`：验证码流程可能需要的附加字段。

Base64 数据会去除可能存在的 data URL 前缀并解码为图片字节，随后传给 `CaptchaChallenge`。

### 10.2 验证码图片定位

程序先使用配置中的验证码选择器；找不到时按 `.verify-img-panel`、canvas、img、背景图等方式查找，并遍历页面 frame。页面元素尚未出现时会等待，而不是立即固定取第一个元素。

### 10.3 OCR 和字符过滤

`LocalClickCaptchaSolver` 调用本地 RapidOCR，保留带文本、置信度和边界框的字符结果，并过滤越界或无效坐标。

当前页面图片右下角有“场馆预约”水印。程序只过滤位于该水印区域的对应字符，不依赖 OCR 输出顺序，也不要求水印四个字全部识别成功。页面改版后需要重新核对水印区域；自动识别仍可能失败。

### 10.4 点击和结果确认

程序按验证码返回的目标字符在 OCR 结果中寻找最佳匹配，优先使用置信度更高的结果。点击坐标会根据验证码原图尺寸和浏览器显示尺寸进行缩放，依次点击目标字符。

三次点击之间默认间隔 50 毫秒，最后一次点击后不再固定等待。已有接口原图时，不再额外截取一张未参与判断的图片。求解器返回 `True` 只代表点击已提交，预约流程仍须检测到支付页才会点击付款入口，不等待原页面的验证码弹窗关闭。自动识别失败、图片缺失、目标字符找不到或结果无法确认时，回退人工模式；验证码调试文件默认不落盘，只有显式开启调试保留时才写入 `captcha-attempt-*` 目录。

## 11. 支付页行为

检测到 URL 或页面标志包含支付信息后：

1. 查找并点击付款入口；
2. 等待支付页面中 `img.payImage` 图片加载；
3. 读取图片像素并转换为 PNG，检查二维码结构后保存为 `payment-qr.png`，非二维码不会发送；
4. 状态更新为 `payment` 并写入 `payment_ready` 事件；
5. 通过带 token 的手机链接发送二维码；
6. 保存 `payment-ready.png`，停留在支付页并轮询支付成功/失败标记，最长等待 60 秒。

程序不会点击最终支付确认按钮。支付成功后将计划标记为已确认；支付失败或超时会刷新场馆页面，重新执行选择日期、场地、同伴、须知和提交订单的完整流程。支付成功和失败提示分别由 `selectors.payment_success_markers`、`selectors.payment_failure_markers` 配置，真实运行前需要按页面实际文案校准。

## 12. 校准、日志和调试产物

运行 `python -m buaa_booking calibrate` 会打开可见浏览器，等待登录并进入场馆页面，生成：

- 场馆截图；
- `element-inventory.json` 元素盘点；
- 页面结构和关键选择器信息。

运行产物位于 `artifacts/`，运行状态位于 `data/`。执行 `run` 时，事件、Python 控制台输出和异常堆栈追加到 `artifacts/<run-date>/run.log`，与当天截图放在一起。主流程成功、失败、跳过或手动中断后均执行清理，按配置时区保留当天及前 4 天；日期目录按目录名判断，其他历史文件按最后修改日期判断。清理跳过链接、重解析点和当前运行目录；删除失败只记日志，不改变主流程结果，下一次运行会重试。进程被强制终止或断电时无法执行收尾。

这些目录可能包含账号页面、姓名、手机号或验证码图片，只应在本机保存，不要提交或同步到外部服务。

## 13. 配置文件和入口命令

- `config/booking.example.json`：可提交的配置模板；
- `config/booking.json`：本机实际配置，不提交版本库；
- `scripts/setup.ps1`：安装项目和 Playwright 依赖；
- `scripts/install_tasks.ps1`：注册 Windows 定时任务。

常用命令：

```powershell
python -m buaa_booking init
python -m buaa_booking setup-secrets
python -m buaa_booking calibrate
python -m buaa_booking serve
python -m buaa_booking prompt
python -m buaa_booking show
python -m buaa_booking run --run-date YYYY-MM-DD --now
```

`run` 命令会进入真实提交流程，可能创建真实订单；运行前确认账号、日期、时间和场馆。测试脚本、调试配置及运行产物保留在本机，不进入运行版本。

## 14. 当前限制

- 网络、校园网/VPN、登录态和验证码接口都可能导致流程停止；
- 最终付款由用户完成；正式流程在支付失败或 60 秒超时后会重走预约流程。
- 当前版本已验证手机二维码链路，不保证 5 秒内点击支付；验证码自动识别仍可能回退人工处理。
